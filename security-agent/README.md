# Security Agent — AI-агент для security-review Pull Request

Агент получает номер Pull Request и **сам решает**, какие проверки запустить: смотрит, что изменилось, вызывает нужные сканеры, сопоставляет находки и выдаёт структурированный вердикт (`APPROVE` / `REQUEST CHANGES` / `NEEDS MANUAL CHECK`).

Это не фиксированный скрипт «запусти A, потом B, потом C». Порядок и набор вызовов определяет LLM на каждом шаге через function calling.

```
PR #N
  │
  ▼
┌──────────────────────────────────────────┐
│ Agent loop (LLM через Groq, tool calling) │
│                                          │
│  plan → choose tool → execute → observe  │◄──┐
│                          │               │   │ ещё данные нужны?
│                          ▼               │   │
│                  enough evidence? ───нет──┼───┘
└──────────────────────────┬───────────────┘
                           │ да
                           ▼
              Отчёт: 🔴 / 🟡 / ✅ + статус сканеров + вердикт
```

## Инструменты агента

| Tool | Что делает | Как реализовано |
|---|---|---|
| `analyze_git_diff(pr_number)` | Список изменённых файлов PR: статус, +/− строк, превью патча | GitHub REST API |
| `run_kics(path)` | Misconfiguration в Dockerfile / Kubernetes / Terraform | `checkmarx/kics` в Docker |
| `run_trivy(path)` | CVE в зависимостях (например, `requirements.txt`) | `aquasec/trivy` в Docker, режим `fs` |
| `query_falco(minutes)` | Runtime-события Falco | **заглушка** (Phase 2) |

Результаты сканеров нормализуются и обрезаются до 15 самых серьёзных находок, чтобы не раздувать контекст модели. Общее число находок передаётся отдельным полем `total_findings`.

## Принципы достоверности

- Агент указывает **только то, что реально вернули инструменты** (конкретные CVE, правила, файлы), и не домысливает уязвимости из знаний модели.
- Если сканер упал или вернул ошибку, это явно отражается в блоке «Статус сканеров», а вердикт `APPROVE` в таком случае запрещён.
- Классификация жёсткая: `CRITICAL`/`HIGH` → 🔴, `MEDIUM` → 🟡, `LOW`/`INFO` → ✅.
- После каждого вызова инструмента в консоль пишется краткий итог (`<- run_trivy: находок: 4`), так что видно, что инструмент вернул, а что агент выводит сам.
- Защита от зацикливания: ограничение числа итераций (`max_iterations=8`), таймауты на запуск сканеров.

## Требования

- Python 3.10+
- Docker (запущенный) — для KICS и Trivy
- Ключ Groq API и GitHub Personal Access Token (право чтения PR)

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

## Запуск

Сканеры читают файлы с диска, поэтому запускай из локального клона репозитория, **на ветке проверяемого PR**:

```bash
git checkout <ветка-PR>

export GROQ_API_KEY="..."
export GITHUB_TOKEN="..."
export GITHUB_REPO="owner/repo"
export PR_NUMBER=2

python3 /путь/к/security_agent.py
```

Ключи берутся только из переменных окружения и в код не попадают. Не коммить их и не публикуй в чатах и логах.

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `GROQ_API_KEY` | Ключ Groq API | — (обязательна) |
| `GITHUB_TOKEN` | GitHub PAT для чтения PR | — (обязательна) |
| `GITHUB_REPO` | Репозиторий в формате `owner/repo` | — (обязательна) |
| `PR_NUMBER` | Номер проверяемого PR | `42` |
| `LOCAL_REPO_PATH` | Путь к локальному клону для сканеров | текущая директория |
| `GROQ_MODEL` | Модель Groq с поддержкой tool calling | `openai/gpt-oss-120b` |
| `DOCKER_DNS` | DNS для контейнера Trivy (если в WSL контейнер не резолвит имена) | не задан |
| `LIST_MODELS` | `1` — вывести модели, доступные твоему ключу, и выйти | — |

## Пример

PR, в котором удалена инструкция `USER appuser` из Dockerfile, а `requests` откачен с 2.31.0 до 2.28.0:

```
=== Итерация 1 ===
[agent] вызывает analyze_git_diff({'pr_number': 2})
    <- analyze_git_diff: файлов в PR: 2
=== Итерация 2 ===
[agent] вызывает run_trivy({'path': '/home/user/ansible-security-monitor'})
    <- run_trivy: находок: 4
=== Итерация 3 ===
[agent] вызывает run_kics({'path': '/home/user/ansible-security-monitor'})
    <- run_kics: находок: 15
=== Итерация 4 ===
[agent] данных достаточно, формирую финальный отчёт
```

Агент нашёл четыре реальных CVE в `requests==2.28.0` (в том числе CVE-2023-32681, исправлено в 2.31.0) и HIGH-находку KICS «Missing User Instruction» в Dockerfile, после чего вынес вердикт `REQUEST CHANGES`.

## Известные ограничения

- Сканеры работают по локальной копии репозитория, а не по коду PR на GitHub: нужно вручную переключиться на ветку PR.
- Trivy работает в режиме `fs` (зависимости), сканирование собранных Docker-образов не подключено.
- Качество отчёта зависит от модели; жёсткие правила в системном промпте снижают, но не исключают ошибки классификации. Вердикт агента — рекомендация, решение принимает человек.
- Агент пока только читает: он не оставляет комментарии в PR и не блокирует merge.
